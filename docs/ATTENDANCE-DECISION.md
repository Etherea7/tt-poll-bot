# Attendance roster — decision record

Status: decided, pending specification
Decided: 2026-08-13 by the project owner
Supersedes: `docs/ATTENDANCE-FEATURE-OPTIONS.md` (exploratory, never committed)

This records **what was chosen and why**, including the alternatives that were
rejected and the reasons, so the analysis is not re-derived later. The
behavioural specification lives in `specs/004-attendance-roster/`.

## Decision

Turn Telegram poll votes into a per-session attendance view by posting **one
roster message per destination per target month**, pinned once and thereafter
updated in place with `editMessageText`. Votes are collected by a **second
GitHub Actions workflow** that calls `getUpdates` on a schedule.

No web page, no Mini App, no database, no hosting provider, no second
deployment target. The feature stays inside the existing repository and its
existing constraints: zero runtime dependencies, no build step, `fetch` plus
JSON, pure functions tested with `node --test`.

## Goal

Members want to see who is attending each TT session without tapping through
four separate polls. Two constraints shaped the decision:

1. **Lightweight** — low ongoing cost and operational burden.
2. **Must not spam the group** — attendance must not add message volume.

## Why not a hosted page or Mini App

The exploratory document recommended a Cloudflare Worker with D1 serving a
mobile-first calendar page. That was rejected. The reasoning matters because it
is the decision most likely to be revisited.

**Members can already see who voted.** The polls are non-anonymous
(`isAnonymous: false`, `src/polls.ts`), so every group member can tap *View
Results* and see exactly who chose each option. A hosted page therefore reveals
**no new information to members**. What it creates is a second copy of personal
attendance data *outside Telegram's access control*, reachable by a link that
can be forwarded.

That single fact reverses the cost comparison:

- Leaving Telegram is what forces an access model, a privacy policy, HTTPS and
  cache isolation, a retention policy, a webhook secret, and — for reliable
  membership checks via `getChatMember` — making the bot a group administrator.
- Staying inside Telegram makes all of that unnecessary. Group membership *is*
  the access control, and it is already in place.

A page buys layout, not information. Layout did not justify the cost.

**The presentation choice, not the hosting choice, is the cost driver.** An
interactive `/whoscoming` command requires sub-second responses, which requires
a webhook, which requires hosting, which requires everything above. Choosing a
message that updates in place removes that entire chain, because a roster has
no latency requirement — nobody needs sub-second freshness on who is coming to
table tennis on Friday.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| Hosted calendar page (Worker + D1, Vercel, self-hosted) | Creates a forwardable copy of personal data outside Telegram; forces access control, privacy policy, retention, hosting, and a second deployment. Buys layout only. |
| Telegram Mini App | All of the above, plus `initData` validation, launch-mode handling, and client-compatibility testing. |
| `/whoscoming` command | Interactive latency forces a webhook and therefore hosting. Also produces one new message per invocation — the spam the owner asked to avoid. |
| Google Calendar / `.ics` feed | Subscription URLs are copied and synced outside the group; clients cache aggressively, so retractions surface late or not at all. |
| Airtable / Sheets / Notion | Still needs a receiver; adds vendor, sharing-control, and API-limit dependencies; makes accidental exposure easier. |
| Webhook receiver (any host) | Correct, but only necessary if the presentation needs low latency. It does not. |

## Verified Telegram behaviour

Checked against the Bot API on 2026-08-13. These bind the design.

- **`poll_answer` carries complete state.** Each update contains the user's
  entire current selection set. An empty set is a retraction. Attendance is
  therefore a full replacement per `(poll_id, user_id)`, never a toggle.
- **Bots only receive `poll` and `poll_answer` for their own polls**, and
  `poll_answer` only for non-anonymous ones. Both are included in the default
  `allowed_updates` set, which excludes only `chat_member`,
  `message_reaction`, and `message_reaction_count`.
- **The `poll` update carries the whole `Poll` object** — `id`, `question`, and
  every option's `text` and `persistent_id`. Because `QUESTIONS` in
  `src/polls.ts` is an exact enum and option text is generated by
  `formatDateOption`/`formatSlotOption`, poll **kind and dates are derivable
  from the update itself**. Only `poll_id → destination` needs storing.
- **Key on `persistent_id`, never on positional `option_ids`.** The Saturday
  poll sets `allow_adding_options` (R40, Bot API 9.6), so option positions are
  not stable. `PollAnswer` supplies `option_persistent_ids` for this reason.
- **Unconsumed updates are retained for at most 24 hours.**
- **`getUpdates` and `setWebhook` are mutually exclusive**, and two concurrent
  `getUpdates` consumers receive HTTP 409.
- **`editMessageText` reuses the same `message_id`** — it creates no new
  message. Editing to identical content fails with *message is not modified*,
  so unchanged renders must be skipped.
- **Message limit is 4096 characters**; the per-group ceiling is roughly 20
  messages per minute.
- The current polls set no `open_period` or `close_date`, so past months' polls
  remain votable indefinitely.

## Design shape

- **Receiver** — a new workflow on `*/30 * * * *` with
  `concurrency: group: attendance`, calling `getUpdates` with
  `allowed_updates: ["poll","poll_answer"]` and a persisted offset. Sequential
  single-consumer polling makes update ordering correct by construction, so no
  ordering metadata is needed.
- **State** — `state/attendance.json`: the offset, per-poll metadata, and
  per-`(poll, user)` selections. Committed by the workflow, mirroring the
  existing `state/delivered.json` pattern.
- **Renderer** — a pure function from sessions to message text, with no I/O,
  guarded by an `assertWithinLimits`-style check against the 4096-character
  limit that refuses or degrades to counts rather than silently truncating.
  This is the existing R41 discipline applied to a new limit.
- **Roster message** — posted after the four polls, pinned with
  `disable_notification: true`, then edited in place. A header line shows the
  last sync time so staleness is visible rather than silent.
- **`cmi`** — ignored when projecting sessions, but the raw selection is
  retained so an organiser can tell "cannot make it" from "has not voted".
- **Member-added Saturday options** — rendered under their own heading with
  their voters, rather than guessed at or hidden.

### Why the "active month" ambiguity disappears

Polls for the following month are posted on the 25th, which made "current
month" ambiguous and led the exploratory document to propose Current/Upcoming
tabs. One roster message *per target month* removes the question: during the
overlap the group simply holds two live roster messages, last month's still
updating and next month's newly posted. No tabs, no default-month rule.

## Accepted trade-offs

These were understood and accepted, not overlooked.

- **Up to ~30 minutes stale.** Acceptable for a roster; it is the reason an
  interactive command is out of scope.
- **No calendar grid, filtering, or month navigation.**
- **A workflow outage longer than 24 hours loses updates permanently**, because
  Telegram discards unconsumed updates. The visible sync timestamp is the
  mitigation; the loss is not recoverable by replay.
- **Scheduled workflows are disabled after 60 days of repository inactivity.**
  The sync job's own commits keep the repository active, but this is a real
  failure mode to monitor.
- **Actions minutes.** Roughly 1,440 runs per month at ~25s is ~600 minutes,
  about 30% of the free private-repository allowance. A public repository or an
  hourly cadence removes the concern.
- **Vote state in Git history is effectively permanent.** Old months can be
  pruned from `state/attendance.json`, but not from the log without rewriting
  shared history, which the branch policy forbids. A database could honour a
  deletion request; this cannot. Accepted because the same data already sits in
  the group's poll results indefinitely and the repository is owner-controlled.
  If this becomes unacceptable, the mitigation is workflow-cache or artifact
  storage with an expiry, at the cost of durability.

## Requirements carried forward

From the exploratory document, these were correct and survive into the
specification: full-replacement semantics, retraction on an empty selection,
destination isolation, display-name refresh without changing identity, poll
delivery never blocked by attendance failure, and no promise to reconstruct
votes cast before collection began.

These were dropped as artifacts of leaving Telegram: webhook authenticity,
controlled access to a web surface, browser and CDN cache isolation, and the
inter-service poll-registration protocol with retry and reconciliation.

## Open questions for the specification

1. Roster message placement — standalone and pinned, or a reply to the Friday
   poll. Standalone is the current preference; replies get buried.
2. Display name format. Telegram already shows full names in poll results, so
   this is a formatting choice rather than a privacy one. First name plus last
   initial on collision is the current preference.
3. Whether the roster covers a month's sessions after that month ends, and when
   its message stops being updated.
4. Whether past months' polls should be closed with `stopPoll` once their
   roster is final.

## Verification still owed

Two behaviours should be confirmed in the test group before implementation:

- that editing a pinned message produces no notification; and
- that `poll` updates arrive with `persistent_id` populated on the live
  Saturday poll, which is the only poll permitting added options.
